# ADR 0009 – Aggregate and JPA Entity Are Separate Classes

## Status
Accepted

## Context

ADR 0001 adopts Spring Data JPA, on organisational grounds, while
`architecture.definition.md` § 4.1 requires `core.domain` to be framework-free and
`modelling.definition.md` requires aggregates to be Always-Valid.

These pull in opposite directions, and the tension is not incidental — it is JPA's
central value proposition. The whole point of an ORM is that your domain classes
*are* your rows. Taking that offer is the default, it is what every Spring tutorial
shows, and it is what the Kotlin JPA plugin is on the classpath to enable.

So the question has to be answered deliberately, because the path of least
resistance answers it one way and the architecture answers it the other.

Three options:

1. **Annotate the aggregate.** `@Entity class MasterLeasingContract`. One class, no
   mapper, Spring Data does the rest.
2. **Two classes with a mapper.** The aggregate in `core.domain`, a
   `*Entity` in `outbound.persistence.write`, and a `*Mapper` between them.
3. **Drop JPA.** Use jOOQ or `JdbcTemplate`, where the question does not arise.

## Decision

**Option 2.** For every persisted aggregate there are three types:

| Type | Package | Role |
|------|---------|------|
| `MasterLeasingContract` | `masterleasing.core.domain.masterleasingcontract` | The aggregate. Framework-free, Always-Valid, private constructor, named factories, no no-arg constructor |
| `MasterLeasingContractEntity` | `masterleasing.outbound.persistence.write` | The row. `@Entity`, `@Id`, `@Column`, mutable `var` properties, no-arg constructor generated by `kotlin("plugin.jpa")`, enforces nothing |
| `MasterLeasingContractMapper` | `masterleasing.outbound.persistence.write` | Converts in both directions |

Supporting decisions that make this hold:

- `ddl-auto=validate`. Flyway owns the schema; Hibernate verifies its mappings
  against it and refuses to start on a mismatch.
- `open-in-view=false`.
- The repository outport returns **detached** aggregates. A caller mutating one
  without calling `update` must not affect the database, and
  `test.definition.md` § 2.3 requires a test asserting exactly that.
- `kotlin("plugin.jpa")` is scoped by annotation, so it opens and adds no-arg
  constructors to `@Entity` classes only. It cannot reach `core.domain`, because
  nothing there carries such an annotation — which is what makes § 4.1 a structural
  guarantee rather than a promise.

## Rationale

### Why not option 1, in detail

Three separate failures, any one of which is sufficient.

**It cannot be Always-Valid.** JPA requires a no-arg constructor and settable
properties. Hibernate instantiates an entity empty and populates it field by field
during reconstitution, regardless of what the constructors say — so the object
demonstrably exists in an invalid state, and the `init` block that was supposed to
be the invariant never runs on that path. `modelling.definition.md`'s central claim
would be false for every loaded aggregate. In Kotlin this is worse than in Java,
because the JPA plugin generates the no-arg constructor *silently*: there is no
visible code admitting the hole.

**It leaks its lifecycle.** A lazily-initialised association throws
`LazyInitializationException` outside a session. That makes the aggregate's
behaviour depend on whether a transaction happens to be open — a property a domain
object must not have, and one that turns a pure unit test into a question about
Hibernate configuration. Making everything eager instead trades the exception for a
join on every load.

**It makes the schema the model.** Renaming a column becomes a domain change;
renaming a domain property becomes a migration. Every persistence concern — column
width, index, nullable, cascade — acquires a vote on the domain's shape. That is
precisely the coupling hexagonal architecture exists to prevent, and it arrives
gradually enough that no single commit looks wrong.

### Why not option 3, given that it removes the problem

jOOQ is the better architectural fit and was rejected on organisational grounds in
ADR 0001: it would make this the only service in the landscape whose persistence
layer nobody else can read, and the point of aligning the stack was to make the
architecture the thing that is unfamiliar, not the tooling.

This ADR is the bill for that decision, and it is being paid explicitly rather than
absorbed.

### What the duplication actually costs

Every persisted field appears three times: aggregate property, entity column,
mapper line. For `MasterLeasingContract` plus `MlcConfiguration` that is roughly
thirty fields across three files.

The cost is **mechanical, local and caught by a test**. A forgotten field is not a
subtle bug: the round-trip test fails, because `test.definition.md` § 2.3 requires
write → read → domain equivalence. Compare that with option 1's costs, which are
structural, global, and caught by nothing.

The mapper is also where several real conversions have to live anyway — `Money` to
`numeric(19,4)`, an enum to its `name()`, an `Instant` to `timestamptz`, a nullable
domain property to a nullable column. Option 1 would still need `@Converter` classes
for those; it would just scatter them.

### Why the "detached" requirement is called out separately

It is the rule JPA breaks most quietly. If a repository returns a mapped aggregate
that still shares references with a managed entity, or if the mapper is bypassed and
the entity itself escapes, then Hibernate's dirty checking writes the caller's
mutations at flush time — and the driver's explicit `update` call becomes
decorative. Every transaction boundary in the system would then be approximately
right and occasionally wrong.

Mapping to a separate class makes this structurally impossible for the aggregate,
but nothing structurally stops a future repository returning an entity. Hence the
port rule and the test.

## Consequences

Positive:

- `core.domain` genuinely has no `jakarta.persistence` import. ArchUnit asserts it
  (ADR 0007).
- Aggregates are Always-Valid on every path, including reconstitution.
- Domain tests need no database, no session, no Spring.
- The schema can change without the domain changing, and vice versa.
- `reconstitute` is a named, explicit operation on the aggregate with documented
  semantics (`modelling.definition.md`, Rehydration Rule), rather than something
  Hibernate does invisibly.

Negative / accepted trade-offs:

- Three files and roughly threefold field duplication per aggregate.
- A field added to an aggregate must be added to the entity, the mapper, a
  migration, and a round-trip assertion. **This is a standing obligation**, and the
  port specs state it: any new mutable field on an aggregate must reach the `update`
  path and an `*IT.update_persists*` assertion in the same increment, or it will not
  survive a write.
- Spring Data's derived query methods return entities, so every repository method
  ends in a mapper call. Slightly more code than the ORM promises.
- No lazy loading across the aggregate boundary, by construction. Loading a master
  contract loads its configuration. That is correct for an aggregate — it is one
  consistency boundary — but it means a future large collection inside an aggregate
  would be a modelling problem, not a fetch-strategy problem. Which is the right
  place for it to be a problem.
