

02 Architecture Handbook (Ports & Adapters for Java + Spring Boot)

Purpose

Define a clean hexagonal architecture: domain-centric, testable, and presentation-friendly.

⸻

Layers and dependency direction

Allowed dependencies:
	•	domain → (nothing)
	•	application → domain
	•	adapters → application, domain
	•	bootstrap (Spring Boot app) → everything

Forbidden:
	•	domain depending on Spring/JPA/HTTP/messaging libraries
	•	application depending on adapter implementations

⸻

Module/package layout (recommended)

Use a multi-module Gradle/Maven setup if you can; otherwise enforce by packages.

Option A: Multi-module (best for talks)
	•	:domain
	•	:application
	•	:adapters
	•	:adapters:web
	•	:adapters:persistence
	•	:adapters:messaging
	•	:bootstrap (Spring Boot)

Option B: Single module packages
	•	com.yourapp.domain..
	•	com.yourapp.application..
	•	com.yourapp.adapters..
	•	com.yourapp.bootstrap..

⸻

What lives where

Domain (domain)

Contains:
	•	Aggregates, entities, value objects
	•	Domain services
	•	Domain events (as types)
	•	Repository interfaces (optionally here; alternatively in application core)

Does NOT contain:
	•	Spring annotations
	•	JPA annotations
	•	Jackson annotations
	•	Logging frameworks
	•	HTTP/Messaging concerns

⸻

Application (application)

Contains:
	•	Use case interfaces (inbound ports)
	•	Use case implementations (application services)
	•	Outbound ports interfaces (repositories, clock, event publisher, external APIs)
	•	Transaction boundaries (either here or bootstrap via annotations)

Does NOT contain:
	•	HTTP controllers
	•	JPA entities/repositories
	•	Kafka/Rabbit/SQS code

⸻

Adapters (adapters)

Contains:
	•	Inbound adapters: REST controllers, message consumers, CLI, schedulers
	•	Outbound adapters: JPA repository implementations, HTTP clients, message publishers

Responsibilities:
	•	Translate external models (DTOs) to domain/application types
	•	Map errors to the outside world (HTTP statuses, error payloads)
	•	Handle serialization/deserialization

⸻

Bootstrap (bootstrap)

Contains:
	•	Spring Boot application class
	•	Wiring configuration:
	•	@Configuration beans for use case implementations
	•	adapter implementations wired into ports

Goal:
	•	Only place where “the whole app” is assembled.

⸻

Ports (interfaces) conventions

Inbound ports (use cases)
	•	Package: application.port.in
	•	Shape: one interface per use case
	•	Methods accept a Command and return a Result (or void + events)

Example naming:
	•	PlaceOrderUseCase
	•	CancelOrderUseCase

Outbound ports
	•	Package: application.port.out
	•	Examples:
	•	OrderRepository
	•	PaymentGatewayPort
	•	EventPublisherPort
	•	ClockPort

⸻

Commands/DTOs separation
	•	Commands belong to application core (use case input).
	•	Web DTOs belong to web adapter.
	•	Avoid using web DTOs directly in use case interfaces.

Mapping flow:
Controller DTO → Command → Domain

⸻

Transactions

Rule:
	•	Transaction boundaries are owned by the application layer (use case).

Practical Spring approach:
	•	Put @Transactional on application service methods (use case implementation).
	•	Avoid @Transactional in adapters/controllers.

⸻

Domain Events publishing strategy

Two-step approach
	1.	Aggregate records domain events during changes.
	2.	Application service persists, then publishes after commit.

Implementation options (pick one for speed):
	•	Simple: publish right after repository save (ok for demos; may publish on rollback unless careful)
	•	Better: transactional event publishing:
	•	store events in-memory during transaction
	•	publish via TransactionSynchronization after commit
	•	Best: Outbox pattern (more work; great for advanced talk)

Recommendation for fast + presentable:
	•	Start with “after commit” publishing via Spring transaction synchronization.

⸻

Persistence approach (JPA) while keeping core clean

Rule: domain objects are not JPA entities.

Patterns:
	•	Create JPA entities in adapters.persistence.jpa
	•	Map:
	•	Domain ↔ JPA Entity with a mapper class
	•	Repository implementation:
	•	Spring Data repository for JPA entity
	•	Adapter implements OrderRepository port and uses mapper

This preserves:
	•	domain purity
	•	testability
	•	the ability to swap persistence later

⸻

API approach (REST) while keeping core clean
	•	Controllers are thin:
	•	parse/validate request
	•	map DTO → command
	•	call use case
	•	map result/errors → HTTP response

Error mapping:
	•	Domain errors → 4xx
	•	Technical errors → 5xx

⸻

“Wiring interface thing” (composition root)

In this project, wiring happens in bootstrap configuration:
	•	@Configuration creates beans for use case implementations
	•	adapters are injected via outbound ports

Rule:
	•	Use case implementations depend only on port interfaces, not on adapter packages.

⸻

Naming conventions (for speed + clarity)
	•	Use cases: VerbNounUseCase (interface), VerbNounService (impl)
	•	Commands: VerbNounCommand
	•	Domain events: NounVerbPastTense (OrderPlaced)
	•	Ports:
	•	inbound: ...UseCase
	•	outbound: ...Port for external systems, ...Repository for persistence

⸻

Testing strategy (fast feedback)

Domain tests (fastest)
	•	Pure unit tests for aggregates/value objects
	•	Assert invariants and emitted events

Application tests
	•	Test use case orchestration with fakes for outbound ports

Adapter tests
	•	Controller tests with mocked use cases (or slice tests)
	•	Persistence adapter tests with Testcontainers (optional)

⸻

Enforce architecture (recommended)

Add an automated “fitness function”:
	•	ArchUnit test that:
	•	domain has no Spring/JPA imports
	•	adapters don’t leak into application
	•	application doesn’t depend on adapters

(If you want, I’ll paste a ready-to-run ArchUnit test for this exact package layout.)

⸻

Quick start implementation order (aligned with docs)
	1.	Create ports (in/out) + commands + result types
	2.	Implement domain aggregate + invariants + events
	3.	Implement use case service (application) with fake ports in tests
	4.	Add persistence adapter + web adapter
	5.	Add after-commit event publishing
